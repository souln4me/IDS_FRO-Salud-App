CU01
Registrando paciente con validación de integridad
Nombre
Registrando paciente con validación de integridad
Actor(es)
Paciente
Resumen
El sistema permite a un nuevo usuario registrarse bajo el rol de Paciente, validando sintácticamente sus datos personales, verificando la unicidad de su identidad y resguardando sus credenciales de acceso.
Frecuencia
Alta
Precondiciones
El actor no debe estar registrado con una cuenta verificada en el sistema.
Descripción
El paciente accede a la interfaz de registro de pacientes para iniciar el proceso [Excepción 1], el sistema despliega el formulario de captura de datos personales, de contacto y credenciales [Excepción 2], el paciente completa íntegramente los campos de nombres, apellidos, RUT, email, teléfono, sexo clínico, dirección (calle, número, departamento y comuna), contacto de emergencia, contraseña y confirmación de contraseña [Excepción 3], el sistema realiza la validación sintáctica de los formatos ingresados, verifica la coincidencia de las contraseñas [Excepción 4], el actor verifica visualmente que su información esté correcta en el diálogo de confirmación y presiona el botón de envío para confirmar la creación de su cuenta [Excepción 5], el sistema ejecuta el cifrado hash de la contraseña, persiste el perfil del paciente en estado inactivo en la base de datos, reemplazando cualquier registro previo con el mismo RUT o correo que nunca haya sido verificado, y despacha el código OTP de activación al correo registrado [Excepción 6].
Excepciones
Excepción 1: El enlace de acceso a la interfaz no carga o está roto. El sistema notifica un error de disponibilidad del servicio. El actor refresca la página o intenta el acceso más tarde.
Excepción 2: Los componentes visuales del formulario no se renderizan correctamente. El sistema registra un error de carga de interfaz en el log. El actor reinicia la aplicación.
Excepción 3: Un campo no cumple el formato requerido, como un RUT inválido, un email mal formado o una contraseña que no cumple la política de seguridad (mínimo ocho caracteres, con letras, números y al menos un símbolo). El sistema muestra un mensaje de error específico con los requisitos incumplidos y detiene el envío. El actor corrige el dato conforme a la máscara de entrada indicada.
Excepción 4: Las contraseñas ingresadas no coinciden. El sistema muestra una alerta de discrepancia y resalta los campos de credenciales. El actor reingresa las claves asegurando su igualdad.
Excepción 5: El actor pierde la conexión a internet justo al momento de presionar el botón de envío. El sistema alerta de un error de red. El actor restablece su conexión y reintenta el envío, debiendo reingresar los datos si la caché no los conservó.
Excepción 6: Ocurre una falla de escritura o pérdida de conexión con el motor de base de datos durante el proceso de persistencia. El sistema detiene el flujo, revierte la transacción, genera un log de error interno y notifica al actor que el servicio no está disponible temporalmente. El actor debe intentar registrarse más tarde.
Poscondiciones
La cuenta del actor queda creada en estado inactivo, con sus datos validados y únicos, a la espera de la verificación de identidad mediante OTP.
Dependencias
RF01, RF03, RF04

CU02
Registrando y acreditando profesional de salud
Nombre
Registrando y acreditando profesional de salud
Actor(es)
Profesional
Resumen
El sistema gestiona la creación de perfiles para profesionales, validando su habilitación mediante una nómina de personal autorizado, guardando su especialidad, configurando su disponibilidad semanal con la modalidad de atención de cada bloque y estableciendo credenciales de acceso seguras.
Frecuencia
Baja
Precondiciones
El Profesional debe contar con sus credenciales de la Superintendencia de Salud y su RUT debe estar previamente registrado y habilitado en la lista de profesionales autorizados por un Administrador.
Descripción
El Profesional ingresa su RUT en el campo respectivo para iniciar su registro [Excepción 1]. El sistema consulta de manera síncrona la vigencia del RUT en la nómina de profesionales autorizados y habilita los campos del formulario para el rol Profesional [Excepción 2]. El Profesional ingresa sus datos de identidad básicos como nombres, apellidos, correo, teléfono, establece una contraseña de acceso y define su especialidad, su número de registro de salud, su reseña curricular y su modalidad general de atención [Excepción 3]. El sistema efectúa la validación sintáctica de los formatos iniciales y despliega la interfaz gráfica para la configuración de la jornada laboral [Excepción 4]. El Profesional estructura su matriz de atención semanal, indicando para cada bloque el día, la hora de inicio, la hora de término y la modalidad de atención (a domicilio, virtual o ambas) [Excepción 5]. El sistema procesa la configuración horaria y presenta en pantalla un resumen solicitando la confirmación de veracidad de los datos [Excepción 6]. El Profesional valida la exactitud de la información ingresada y otorga el consentimiento final para terminar el proceso de alta [Excepción 7]. El sistema ejecuta el cifrado hash de la contraseña, persiste el perfil y la disponibilidad en la base de datos centralizada y despacha el código OTP de activación al correo registrado [Excepción 8].
Excepciones
Excepción 1: El Profesional ingresa un RUT que no cumple con el formato algorítmico válido. El sistema resalta el campo de entrada indicando un error de sintaxis. El Profesional corrige el RUT ingresado.
Excepción 2: El RUT ingresado no figura en la nómina de profesionales autorizados o figura como inhabilitado. El sistema detiene el registro, alerta mediante una ventana emergente que el usuario no está habilitado y bloquea el avance del flujo. El Profesional verifica su RUT o contacta a la administración.
Excepción 3: El Profesional ingresa un número de registro o teléfono con caracteres alfabéticos no permitidos, o establece una contraseña que no cumple la política de seguridad (mínimo ocho caracteres, con letras, números y al menos un símbolo). El sistema resalta los campos con error y muestra los requisitos faltantes en pantalla. El Profesional corrige los datos según el estándar exigido.
Excepción 4: La interfaz de configuración de disponibilidad no carga por un error de comunicación interna con el servidor. El sistema muestra un mensaje de tiempo de espera agotado. El Profesional refresca la página para reintentar la carga.
Excepción 5: El Profesional intenta finalizar sin haber agregado ningún bloque horario a su jornada. El sistema detiene el envío y muestra la alerta de agenda vacía. El Profesional agrega al menos un bloque horario.
Excepción 6: El sistema experimenta una interrupción o latencia excesiva al compilar los datos para generar el resumen. El sistema muestra una alerta de error de carga en el componente. El Profesional presiona el botón de reintentar para volver a solicitar el despliegue del resumen.
Excepción 7: El Profesional decide cancelar el proceso rechazando la confirmación de veracidad. El sistema cierra el diálogo y mantiene los datos en pantalla para su revisión sin guardar nada. El Profesional corrige la información o cierra la ventana de registro.
Excepción 8: Ocurre una falla de escritura en el servidor de base de datos durante la persistencia final. El sistema revierte la transacción, genera un log de error y notifica la imposibilidad de guardar el perfil. El Profesional contacta al soporte técnico para reportar la incidencia.
Poscondiciones
La cuenta del Profesional queda registrada con sus credenciales cifradas y su matriz de disponibilidad horaria con modalidad por bloque, pendiente de activación mediante la verificación OTP.
Dependencias
RF02, RF03, RF04, RF59

CU03
Controlando unicidad de cuentas de usuario
Nombre
Controlando unicidad de cuentas de usuario
Actor(es)
Paciente / Profesional
Resumen
El sistema verifica que el RUT y el correo no pertenezcan a una cuenta verificada antes de guardar un nuevo usuario para evitar duplicados; los registros previos que nunca completaron su verificación se informan y se reemplazan.
Frecuencia
Alta
Precondiciones
El Paciente / Profesional debe haber completado y enviado el formulario de registro con datos sintácticamente válidos.
Descripción
El Paciente / Profesional envía el formulario de registro solicitando la creación de una nueva cuenta en la plataforma [Excepción 1], el sistema recibe los parámetros y realiza una búsqueda indexada en la base de datos para validar que el RUT no pertenezca a una cuenta verificada [Excepción 2], el Paciente / Profesional aguarda la respuesta del motor de validación en la pantalla de procesamiento [Excepción 3], el sistema verifica la disponibilidad del correo electrónico y autoriza la persistencia final del registro si se cumple la condición de unicidad; si existe un registro previo sin verificar con los mismos datos, informa que será reemplazado y continúa [Excepción 4].
Excepciones
Excepción 1: Se detecta una interrupción en el envío de los paquetes de datos por falla de red. El sistema muestra una alerta de pérdida de conexión persistente. El Paciente / Profesional verifica su acceso a internet y reintenta la operación.
Excepción 2: El RUT ingresado ya se encuentra registrado en una cuenta verificada del repositorio central. El sistema aborta el flujo de registro y emite una notificación de cuenta existente. El Paciente / Profesional utiliza la opción de recuperación de contraseña o ingresa un documento distinto.
Excepción 3: El tiempo de respuesta de la consulta a la base de datos excede el umbral de latencia permitido. El sistema informa que el servicio de validación no está disponible momentáneamente. El Paciente / Profesional intenta el registro nuevamente tras unos minutos.
Excepción 4: El correo electrónico proporcionado ya está vinculado a una cuenta verificada. El sistema detiene el proceso y resalta el campo de email con una advertencia de duplicidad. El Paciente / Profesional introduce una dirección de correo alternativa para completar el alta.
Poscondiciones
Se asegura que el nuevo registro es único entre las cuentas verificadas y se avanza en el proceso de creación de cuenta.
Dependencias
RF01, RF02, RF03, RNF05.

CU04
Verificando identidad mediante código OTP
Nombre
Verificando identidad mediante código OTP
Actor(es)
Paciente / Profesional
Resumen
El sistema envía por correo electrónico un código de un solo uso para validar la identidad del usuario y activar su cuenta recién registrada.
Frecuencia
Alta
Precondiciones
El Paciente / Profesional debe haber pasado el control de unicidad de registro.
Descripción
El Paciente / Profesional solicita el envío del código de seguridad para iniciar el proceso de validación de su identidad [Excepción 1], el Sistema genera un código OTP de seis dígitos con vigencia de diez minutos y lo transmite al correo electrónico registrado [Excepción 2], el Paciente / Profesional ingresa la secuencia numérica recibida en el formulario de activación de la plataforma [Excepción 3], el Sistema comprueba la exactitud y vigencia del código para proceder con la activación definitiva de la cuenta en la base de datos [Excepción 4].
Excepciones
Excepción 1: El servicio de correo presenta una caída que impide el envío. El Sistema registra el fallo en la bitácora de auditoría y alerta al usuario indicando la causa. El Paciente / Profesional presiona el botón de reintento, habilitado tras sesenta segundos.
Excepción 2: La dirección de correo es marcada como inalcanzable por el proveedor. El Sistema muestra una notificación de error en el envío del código. El Paciente / Profesional vuelve a registrarse con un correo válido.
Excepción 3: El Paciente / Profesional introduce un código que no coincide con el generado o que ya ha superado su tiempo de vida útil. El Sistema invalida el intento, limpia los campos y solicita la generación de una nueva clave. El Paciente / Profesional solicita un nuevo código OTP desde la interfaz.
Excepción 4: Se produce una falla de escritura en el servidor durante el cambio de estado del perfil. El Sistema registra el fallo en la bitácora de auditoría, lanza una excepción de persistencia y mantiene la cuenta como no activa. El Paciente / Profesional refresca la página e intenta el proceso nuevamente.
Poscondiciones
La cuenta del Paciente / Profesional cambia a estado "Activada" y el actor es dirigido al inicio de sesión.
Dependencias
RF01, RF02, RF04, RNF05

CU05
Autenticando usuario y resguardando credenciales
Nombre
Autenticando usuario y resguardando credenciales
Actor(es)
Paciente / Profesional / Administrador
Resumen
El sistema permite el inicio de sesión validando RUT y contraseña, utilizando algoritmos de hashing para comparar de forma segura, y registra la sesión del dispositivo para que pueda ser revocada.
Frecuencia
Muy Alta
Precondiciones
El Paciente / Profesional / Administrador debe tener una cuenta activa.
Descripción
El Paciente / Profesional / Administrador ingresa su RUT y su contraseña en el portal de acceso para iniciar la sesión [Excepción 1], el Sistema captura las credenciales y aplica el algoritmo de hashing unidireccional a la contraseña proporcionada [Excepción 2], el Paciente / Profesional / Administrador permanece en la interfaz de espera mientras se realiza la consulta de seguridad en el repositorio de identidades [Excepción 3], el Sistema compara el hash resultante con el registro almacenado en la base de datos, genera un Token de Acceso y registra la sesión del dispositivo para conceder la entrada si la validación es exitosa [Excepción 4].
Excepciones
Excepción 1: El Paciente / Profesional / Administrador introduce un formato de RUT no reconocido por las reglas de validación del lado del cliente. El Sistema resalta el campo de entrada con un mensaje de error de formato. El Paciente / Profesional / Administrador corrige el RUT según el estándar permitido.
Excepción 2: El servicio de criptografía interno no se encuentra disponible para procesar el hash de la contraseña. El Sistema emite un código de error de servicio y registra la incidencia en el log de seguridad. El Paciente / Profesional / Administrador intenta realizar el ingreso nuevamente tras unos segundos.
Excepción 3: La conexión con el servidor de base de datos se interrumpe durante la consulta de los hashes. El Sistema informa sobre la indisponibilidad momentánea del servicio de autenticación. El Paciente / Profesional / Administrador refresca la página para restablecer el canal de comunicación.
Excepción 4: Los hashes comparados no coinciden debido a una contraseña incorrecta, o el Paciente / Profesional / Administrador no existe o su cuenta no está activa. El Sistema deniega el acceso, registra el intento fallido en la bitácora de auditoría con el RUT, el motivo y la dirección IP, y muestra una alerta de credenciales inválidas. El Paciente / Profesional / Administrador verifica sus datos e ingresa la contraseña correcta.
Poscondiciones
Se inicia una sesión segura para el usuario, visible y revocable desde la configuración de seguridad de su cuenta.
Dependencias
RF05, RF08, RNF03

CU06
Solicitando restablecimiento de credenciales
Nombre
Solicitando restablecimiento de credenciales
Actor(es)
Paciente / Profesional / Administrador
Resumen
El Paciente / Profesional / Administrador solicita cambiar su contraseña olvidada mediante su correo, recibiendo un OTP automatizado para autorizar el cambio.
Frecuencia
Media
Precondiciones
El Paciente / Profesional / Administrador debe estar registrado en el sistema con un correo electrónico válido.
Descripción
El Paciente / Profesional / Administrador accede a la opción de "Olvidé mi contraseña" para dar inicio al flujo de recuperación de credenciales [Excepción 1], el Sistema presenta la interfaz de captura de datos solicitando el correo electrónico vinculado a la cuenta [Excepción 2], el Paciente / Profesional / Administrador ingresa su dirección de correo electrónico en el campo habilitado para tal fin [Excepción 3], el Sistema realiza la búsqueda en la base de datos y envía un código OTP con vigencia de diez minutos al correo si el Paciente / Profesional / Administrador es identificado [Excepción 4].
Excepciones
Excepción 1: El enlace de recuperación presenta un error de redireccionamiento interno. El Sistema registra el fallo de navegación y muestra un mensaje de servicio no disponible momentáneamente. El Paciente / Profesional / Administrador intenta el acceso nuevamente pasados unos minutos.
Excepción 2: La interfaz de recuperación no se renderiza por falta de conexión con el servidor de aplicaciones. El Sistema lanza una alerta de tiempo de espera agotado. El Paciente / Profesional / Administrador recarga la aplicación.
Excepción 3: El Paciente / Profesional / Administrador introduce una dirección con un formato de dominio inválido o incompleto. El Sistema bloquea el envío y resalta el error sintáctico bajo el campo de texto. El Paciente / Profesional / Administrador corrige la cadena de texto ingresada según el formato estándar.
Excepción 4: El correo electrónico ingresado no existe en los registros de la plataforma. El Sistema simula el proceso de despacho y muestra un mensaje genérico de envío exitoso para evitar la enumeración de Paciente / Profesional / Administrador por parte de terceros.
Poscondiciones
El Paciente / Profesional / Administrador recibe un OTP válido para proceder con el cambio de contraseña.
Dependencias
RF06, RF07

CU07
Ejecutando cambio de contraseña
Nombre
Ejecutando cambio de contraseña
Actor(es)
Paciente / Profesional / Administrador
Resumen
El sistema procesa y guarda una nueva contraseña segura tras validar el código OTP ingresado por el usuario, cerrando todas sus sesiones activas.
Frecuencia
Media
Precondiciones
El Paciente / Profesional / Administrador debe poseer un OTP válido, obtenido desde la recuperación pública de credenciales (CU06) o solicitado desde la configuración de seguridad de su cuenta con sesión iniciada.
Descripción
El Paciente / Profesional / Administrador ingresa el código OTP de validación en el campo correspondiente de la interfaz para verificar su identidad [Excepción 1], el Sistema comprueba la integridad y vigencia del código habilitando inmediatamente el formulario de ingreso de nueva credencial [Excepción 2], el Paciente / Profesional / Administrador escribe la nueva contraseña asegurándose de cumplir con los criterios de complejidad y seguridad exigidos [Excepción 3], el Sistema ejecuta el algoritmo de hashing, persiste el nuevo registro en la base de datos, revoca todas las sesiones activas del usuario y registra el cambio en la bitácora de auditoría [Excepción 4].
Excepciones
Excepción 1: El Paciente / Profesional / Administrador introduce caracteres alfabéticos en un campo que solo admite entradas numéricas. El Sistema bloquea la entrada de datos inválidos mediante una máscara de validación en tiempo real. Paciente / Profesional / Administrador corrige el ingreso utilizando únicamente dígitos.
Excepción 2: El código ingresado no coincide con el registro activo o el tiempo de validez ha expirado. El Sistema deniega la habilitación del formulario y muestra una alerta de código inválido. El Paciente / Profesional / Administrador solicita el reenvío de un nuevo código OTP.
Excepción 3: La contraseña proporcionada no alcanza el nivel de robustez requerido por las políticas de seguridad (mínimo ocho caracteres, con letras, números y al menos un símbolo). El Sistema resalta los requisitos incumplidos y mantiene deshabilitado el botón de confirmación. El Paciente / Profesional / Administrador modifica la clave hasta satisfacer todos los criterios técnicos.
Excepción 4: Se produce una interrupción en la comunicación con el servidor de datos durante el proceso de guardado. El Sistema notifica que la operación no pudo completarse y registra el fallo de persistencia. El Paciente / Profesional / Administrador reintenta el envío del formulario una vez restablecida la conexión.
Poscondiciones
La contraseña del Paciente / Profesional / Administrador es actualizada en la base de datos y todas sus sesiones quedan cerradas; debe iniciar sesión nuevamente con la clave nueva.
Dependencias
RF05, RF06, RF07, RF08, RNF08

CU08
Gestionando sesiones y tokens de acceso
Nombre
Gestionando sesiones y tokens de acceso
Actor(es)
Paciente / Profesional / Administrador
Resumen
El Paciente / Profesional / Administrador visualiza sus sesiones activas en distintos dispositivos y puede cerrarlas remotamente, invalidando los tokens.
Frecuencia
Baja
Precondiciones
El Paciente / Profesional / Administrador debe tener una sesión activa.
Descripción
El Paciente / Profesional / Administrador accede al apartado de seguridad de su cuenta para gestionar sus sesiones [Excepción 1], el Sistema consulta el registro de sesiones y despliega la lista de sesiones activas con dispositivo, dirección IP y fecha de inicio, marcando la sesión del dispositivo actual [Excepción 2], el Paciente / Profesional / Administrador selecciona una sesión específica de la lista y activa la opción para revocar el acceso remoto [Excepción 3], el Sistema desactiva la sesión en el registro; en la siguiente petición desde el dispositivo destino, el Token de Acceso es rechazado y la sesión se cierra con un aviso [Excepción 4].
Excepciones
Excepción 1: El enlace a los ajustes de seguridad no responde debido a un error de ruteo en la aplicación. El Sistema devuelve un mensaje de error de navegación. El Paciente / Profesional / Administrador recarga la aplicación para restablecer los parámetros de acceso.
Excepción 2: El servicio de gestión de identidades no logra recuperar la lista de sesiones activas. El Sistema muestra una advertencia indicando que la información de los dispositivos no está disponible momentáneamente. El Paciente / Profesional / Administrador presiona el botón de actualización manual para reintentar la carga.
Excepción 3: El Paciente / Profesional / Administrador intenta revocar una sesión que ya fue cerrada o expiró durante la visualización de la lista. El Sistema notifica que esa sesión ya no está activa y actualiza la vista removiendo el dispositivo. El Paciente / Profesional / Administrador continúa gestionando sus otras conexiones activas.
Excepción 4: El servidor experimenta una falla de persistencia al intentar desactivar el registro de sesión. El Sistema registra la excepción y solicita al Paciente / Profesional / Administrador reintentar la operación. El Paciente / Profesional / Administrador presiona nuevamente el botón de revocación.
Poscondiciones
La sesión seleccionada queda terminada y el dispositivo pierde el acceso en su siguiente petición al servidor.
Dependencias
RF05, RF08, RNF03, RNF08

CU09
Configurando privacidad de datos de contacto
Nombre
Configurando privacidad de datos de contacto
Actor(es)
Paciente
Resumen
El paciente ajusta los parámetros de su perfil para definir qué datos de contacto serán visibles para el profesional que lo atiende.
Frecuencia
Baja
Precondiciones
El paciente debe estar autenticado en el sistema.
Descripción
El Paciente navega hacia el módulo de privacidad dentro de la configuración de seguridad de su cuenta [Excepción 1], el Sistema presenta la matriz de opciones de visibilidad: mostrar dirección y mostrar teléfono [Excepción 2], el Paciente ajusta los parámetros de privacidad activando o desactivando cada interruptor [Excepción 3], el Sistema valida las nuevas preferencias, actualiza el registro del paciente y deja constancia del cambio en la bitácora de auditoría [Excepción 4].
Excepciones
Excepción 1: El módulo de privacidad no se encuentra disponible por una falla en el servidor de aplicaciones. El Sistema muestra un mensaje de error de carga de componente. El Paciente intenta acceder nuevamente tras recargar la aplicación.

La cita del paciente está agendada o confirmada, y existe un Financiador con convenio activo.
Descripción
El Paciente selecciona el Financiador e inserta el folio del bono en el formulario de pagos de la aplicación móvil [Excepción 1], el Sistema valida el formato del folio, encapsula las variables y dispara el payload hacia el servicio de validación del Financiador a través de la capa adaptadora [Excepción 2], el Paciente aguarda la resolución observando el indicador de estado de red [Excepción 3], el Sistema procesa el retorno afirmativo y persiste el bono validado con su monto de cobertura y copago [Excepción 4].
Excepciones
Excepción 1: El Paciente ingresa un folio que incumple el formato exigido. El Sistema detiene el envío renderizando el aviso en la interfaz. El Paciente corrige el formato del código.
Excepción 2: El Sistema recibe del Financiador una respuesta de rechazo por discrepancia de autenticación. El Sistema registra el bono como no validado y lo informa. El Paciente verifica el folio con su institución o procede con la tarifa completa particular.
Excepción 3: El Sistema alcanza el límite de espera sin respuesta del Financiador tras los reintentos automáticos. El Sistema informa que el bono no pudo registrarse. El Paciente reintenta más tarde.
Excepción 4: El Sistema experimenta rechazo de escritura por bloqueos de tabla en la persistencia. El Sistema aplica un retardo progresivo y reintenta la escritura. El Sistema asienta el registro exitosamente.
Poscondiciones
El bono queda validado y el copago de la cita calculado; sin bono validado, la cita mantiene el arancel completo.
Dependencias

CU67

Nombre

Frecuencia

Poscondiciones
El registro de pagos del paciente y su inventario de sesiones quedan actualizados, asegurando la cuadratura.

CU68
Intercambiando Datos con Proveedor Externo
Nombre
Intercambiando Datos con Proveedor Externo
Actor(es)
Proveedor Externo
Resumen
Modificación estructural del formato de los paquetes de datos para asegurar interoperabilidad aislada con servicios de terceros.
Frecuencia
Muy Alta, operando como middleware para la validación de bonos con el Financiador; los proveedores OpenAI, I-Med y pasarela de pago quedan registrados en la capa para su conexión futura.
Precondiciones
El flujo de negocio gatilla un requerimiento de lectura o escritura que excede la arquitectura interna del ecosistema FRO Salud.
Descripción
El Sistema transmite la petición con la estructura de datos estandarizada hacia el Proveedor Externo [Excepción 1], el Proveedor Externo procesa la carga útil y retorna el paquete de datos con la respuesta operativa [Excepción 2], el Sistema recibe la información externa evaluando los tiempos de latencia de la transacción [Excepción 3], el Proveedor Externo entrega la estructura final, el Sistema transforma el modelo al estándar interno asegurando la integridad [Excepción 4] y persiste el registro de la transacción en la bitácora de auditoría.
Excepciones
Excepción 1: El Sistema detecta que el objeto a enviar carece de atributos obligatorios. El Sistema aborta la transmisión, registra el fallo de sintaxis en la bitácora de auditoría y notifica el error al flujo de negocio original.
Excepción 2: El Proveedor Externo rechaza la conexión por indisponibilidad de red o caída del servicio. El Sistema captura el código de error, lo documenta en la bitácora de auditoría y activa la lógica de reintento automático.
Excepción 3: El Sistema identifica que el tiempo de respuesta excede el umbral de seguridad definido. El Sistema interrumpe la escucha y registra la transacción con estado de latencia crítica en la bitácora de auditoría.
Excepción 4: El Proveedor Externo envía un formato de datos que diverge del esquema documentado. El Sistema aísla el paquete incompatible guardándolo en la bitácora de auditoría y retorna una excepción estandarizada al núcleo de la aplicación.
Poscondiciones
La segregación en la capa adaptadora asegura que el núcleo de la aplicación permanezca agnóstico frente a actualizaciones de esquemas de proveedores.
Dependencias
RF66, RF68, RF69.

CU69
Registrando en Bitácora de Transacciones Externas
Nombre
Registrando en Bitácora de Transacciones Externas
Actor(es)
Proveedor Externo
Resumen
Captura e inserción inalterable de los paquetes de datos y latencias asociadas a las peticiones de integración con terceros en la bitácora de auditoría.
Frecuencia
Muy Alta, ejecutada como subproceso paralelo en cada interacción de red hacia nodos externos.
Precondiciones
El adaptador de API inicializa la construcción de un paquete de datos dirigido a un servicio foráneo.
Descripción
El Sistema inicia la captura de metadatos y emite la petición de datos hacia el Proveedor Externo [Excepción 1], el Proveedor Externo procesa la solicitud y despacha la respuesta técnica al origen [Excepción 2], el Sistema recibe la información, calcula la latencia y persiste el registro consolidado en la bitácora de auditoría con acción de integración externa (proveedor, operación, estado, código de respuesta, latencia, intentos y payloads enviado y recibido) [Excepción 3].
Excepciones
Excepción 1: El Sistema detecta la carencia de la credencial de seguridad requerida para la conexión. El Proveedor Externo rechaza la petición y el Sistema la registra, alertando al Administrador para actualizar las credenciales.
Excepción 2: El Proveedor Externo omite la respuesta superando el umbral de tiempo de espera definido. El Sistema detiene la escucha y almacena la incidencia como un error de latencia crítica en la bitácora.
Excepción 3: El Sistema experimenta un error de persistencia al intentar guardar el registro. El Sistema informa el fallo en el log del servidor y continúa la operación principal, notificando la inconsistencia técnica al Administrador.
Poscondiciones
La bitácora de auditoría asimila un registro histórico completo habilitando la trazabilidad técnica y la depuración de la interoperabilidad.
Dependencias
RF13, RF68, RF69, RNF14.

CU70
Ejecutando Lógica de Reintento ante Fallos
Nombre
Ejecutando Lógica de Reintento ante Fallos
Actor(es)
Proveedor Externo
Resumen
Iteración temporal controlada de peticiones de red destinadas a mitigar interrupciones causadas por inestabilidad de infraestructura externa.
Frecuencia
Baja, sujeta exclusivamente al reconocimiento de códigos de error de capa de transporte o indisponibilidad de servidor.
Precondiciones
El adaptador de API recibe un código de error de conectividad, un tiempo de espera agotado o un error HTTP de la familia 500 desde un nodo externo.
Descripción
El Proveedor Externo emite un código de error de red tras la petición integradora inicial [Excepción 1], el Sistema incrementa el contador de intentos de la petición en memoria [Excepción 2], el Proveedor Externo recibe la petición reemitida portando un retraso temporal progresivo (exponencial, con tope) [Excepción 3], el Sistema lee el código de estado afirmativo y reinicia la variable del ciclo [Excepción 4].
Excepciones
Excepción 1: El Proveedor Externo emite un error de validación por formato incompatible, provocando que el Sistema aborte el ciclo iterativo y documente el rechazo en la bitácora técnica.
Excepción 2: Una falla al registrar el contador de intentos obliga al Sistema a inicializar una variable temporal en memoria local para reanudar el ciclo de contingencia.
Excepción 3: El Proveedor Externo persiste en el error tras alcanzar el límite máximo de cuatro intentos, forzando al Sistema a suprimir las peticiones, registrar el evento crítico y transferir el control a la interfaz originaria.
Excepción 4: Tras la respuesta exitosa, el Sistema experimenta un fallo al consolidar la finalización del ciclo, ejecutando una rutina de estabilización de recursos y notificando la inconsistencia al Administrador.
Poscondiciones
La transacción externa consolida su estado final previniendo bloqueos indefinidos de hilos de ejecución en el servidor principal.
Dependencias
RF68, RF69, RF70, RNF14.

Segregando interfaces según rol de acceso
Nombre
Segregando interfaces según rol de acceso
Actor(es)
Paciente / Profesional / Administrador
Resumen
El Sistema decodifica el Token de Acceso JWT y renderiza un entorno de Vista estructuralmente independiente para cada rol.
Frecuencia
Ejecución síncrona en cada inicio de sesión

El Paciente, Profesional o Administrador posee credenciales válidas y una cuenta activa en la plataforma.
Descripción
El Paciente / Profesional / Administrador ingresa sus credenciales de acceso en la interfaz de autenticación solicitando la entrada [Excepción 1], el Sistema evalúa la carga útil del token identificando el Rol de Acceso acreditado en la matriz de permisos [Excepción 2], el Paciente / Profesional / Administrador interactúa con los módulos y rutas de navegación habilitadas para su perfil [Excepción 3], el Sistema renderiza los componentes visuales bloqueando accesos no autorizados a datos sensibles mediante validación síncrona en el servidor [Excepción 4].
